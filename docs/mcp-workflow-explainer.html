模型 × 工具 × MCP

模型会思考，
MCP 让它能办事。

把 MCP 想成模型与外部工具之间的标准插头。它不会改变模型的大脑；它让模型能按统一方式请求工具，再根据工具返回的结果继续工作。

先记住这一句MCP 的价值不在“让模型突然变聪明”，而在复杂任务中，提供更合适、更可控的工具路径。

一个生活里的比喻

🧑🏻‍🔬

模型像研究员。它会分析问题，但它看不到你的硬盘，也不能凭空操作文件。
MCP 像统一的服务窗口。模型按约定递交请求，文件工具去查，再把结果送回来。

模型：决定下一步MCP：约定怎么请求工具：真正执行读取

对当前这个项目，实际到哪了？

ops_batch 能在一次 MCP 调用中预检并执行最多 512 个允许的文件步骤；grep_many 可在一次目录遍历中搜多个字面词。单步检索先只回传查询词对应的路径和行号，命中行文本留在本机；ops_result 再按查询词、路径前缀或其他条件分页。SQLite 索引让过滤只读取相关结果。这样可减少重复扫描、工具往返和无关回传；模型 token 是否下降仍要用同一模型和任务实测。它不等于任意代码执行 PTC，也不保证达到视频展示的 27.7 倍。

当前：单次多词检索 + 索引过滤 + 位置优先预览 + 本地分页

什么时候会有帮助？

01文件少、任务简单

直接读取就够了，MCP 可能没有额外收益。

02文件多、结果很长

先返回有限摘要，再查看相关片段，能减少无关内容。

03同类任务反复做

一致的工具契约可复用在多个支持 MCP 的客户端中。

04要批量修改文件

写入批次附上幂等键；网络重试复用同一键，服务不会重复执行。
