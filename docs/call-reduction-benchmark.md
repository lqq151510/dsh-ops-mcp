# 工具调用量对照基准

本基准用来回答：在真实客户端和同一模型下，`ops_batch` 是否减少 MCP 工具调用、模型轮次和 token。它不把批次中的文件步骤数当成工具调用数，也不把一次 MCP 调用直接等同于一次模型轮次。

## 对照方法

1. 固定模型、提示词、项目快照、任务目标和客户端版本；关闭会改变文件内容的并发任务。
2. 每个任务先用现有单项工具完成，记录每次 `ops_inspect_local_file`、`ops_glob`、`ops_grep` 调用；再用 `ops_batch` 完成同一目标，按实际需要把每次 `ops_result` 也计入。
3. 交替执行两种方式各 5 次。写入任务每轮恢复同一份初始文件，避免后一次拿到不同前置状态。
4. 从客户端调用记录统计 MCP 调用次数和模型轮次；从模型用量记录统计输入/输出 token；记录耗时及任务结果是否正确。
5. 报告每项任务的中位数和范围。只有结果正确率相当、且调用或 token 中位数下降，才报告对应指标的节省；分别报告，不外推为所有任务的收益。

## 建议任务集

| ID | 任务 | 单项工具基线 | 批处理路径 |
| --- | --- | --- | --- |
| S1 | 在多份源文件里搜一个字面词，返回相关行 | `ops_grep` | 单步 `grep` |
| S2 | 搜两个词并读取命中的文件片段 | 多次 `ops_grep`，再对命中文件调用 `ops_inspect_local_file` | `grep` + `read_text` 步骤，完整命中用 `ops_result` 过滤 |
| S3 | 列出匹配文件并统计行数 | `ops_glob` 后对每个匹配文件调用 `ops_inspect_local_file`，由模型计数 | `glob` + 多个 `count_lines` 步骤 |
| S4 | 比较两份已确认相同的小文件并报告行数 | 分别调用 `ops_inspect_local_file`，由模型比较和计数 | `assert_equal` + 两个 `count_lines` 步骤组成一个批次 |
| S5 | 执行大搜索并回答一个指定问题 | `ops_grep` 分批或重复调用并查看结果 | `grep` 批次；先看预览，只有不足以回答时再调 `ops_result` |

若基线工具无法完成某一步（例如它没有行数统计），记录该差异，不把本地脚本或模型臆测的计数冒充同口径结果。

## 真实模型 + stdio MCP 对照

2026-10-15 使用本机 OpenClaw 配置的 `deepseek/deepseek-flash`，在临时目录创建 3 个合成文件，让模型读取每个文件首行并准确汇总。基线提供单项读取工具，批处理组提供 `ops_batch` / `ops_result`；每组跑 5 次并交替顺序。每次都做一次模型规划、执行 MCP 调用，再做一次模型总结。MCP 调用通过真实 stdio 服务完成。

| 方式 | 每次 MCP 调用数 | MCP 调用中位数 | 模型请求 | MCP 耗时中位数 | 输入 token 中位数* | 输出 token 中位数* | 五次答案正确 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | --- |
| 单项读取 | `3, 3, 3, 3, 3` | 3 | 10 次 | 4 ms | 932 | 138 | 是 |
| 批量读取 | `1, 1, 1, 1, 1` | 1 | 10 次 | 6 ms | 1,081 | 157 | 是 |

在这个特定任务里，批处理每次少 2 次 MCP 调用，调用数下降约 66.7%；模型请求数没有变化。小样本的 MCP 耗时没有改善。模型输入 token 中位数反而高约 16%，输出 token 高约 14%；提示内容不同，且 OpenClaw 的系统提示和缓存会影响这些统计，因此不能把它们解释成普遍的 token 变化。

模型被要求输出 JSON 工具计划，由测试驱动器按计划实际调用 MCP，再把结果发回模型总结；这验证了模型参与的计划 -> MCP 执行 -> 模型总结闭环，但不是客户端 UI 内置的自动函数调用路径。测试只使用临时合成文件，没有读取或发送仓库内容。此前 202 步批次演示仍只证明批次承载能力。

## 有副作用批次的重试安全验收

2026-10-15 增加 `idempotency_key` 后，运行 19 项 Python 单元测试（全部通过），覆盖相同键重试、并发重试、结果库重启、异常进程恢复、释放结果、键与步骤不匹配、允许目录不匹配，以及文件写入后模拟响应丢失。另由 `deepseek/deepseek-flash` 单轮生成一份合成写入计划，再由本地测试驱动器通过重启前后的真实 stdio MCP 进程调用 `ops_batch`，并分页调用 `ops_result`：首次状态为 `completed`，重启后的重放返回同一个 `details_ref` 且 `deduplicated=true`，临时文件 inode 不变，完整结果仍为两行。

这证明模型生成的参数经本地驱动器提交后，MCP 服务能去重重试；OpenClaw 本次 `bridgeCalls.call=0`，所以没有验证模型宿主自动选择并直接调用 MCP 工具的路径。测试文件只存在于临时目录。
